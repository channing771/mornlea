# authoritative-crafting Delta

## MODIFIED Requirements

### Requirement: 固定配方具有稳定语义

系统 SHALL 定义十三条稳定固定形状配方，recipe ID、形状、原料、数量和产物 MUST 由服务端定义，客户端不得声明或覆盖这些值。形状以裁边后的宽高与非空格序列表达，匹配遵守 `authoritative-grid-crafting` 的裁边与水平镜像规则：

- recipe ID `1`：2×2 石头，产出 4 个石砖。
- recipe ID `2`：3×3 圆石圆环（中格为空），产出 1 个熔炉。
- recipe ID `3`：3×3 铁锭，产出 1 个铁块。
- recipe ID `4`：顶排 3 个石头、中列 2 根木棍，产出 1 把石镐。
- recipe ID `5`：顶排 3 个铁锭、中列 2 根木棍，产出 1 把铁镐。
- recipe ID `6`：3×3 橡木木板圆环（中格为空），产出 1 个箱子。
- recipe ID `7`：1 个橡木原木，产出 4 个橡木木板。
- recipe ID `8`：2×2 玻璃，产出 4 个发光方块。
- recipe ID `9`：2 个石头纵列旁接 2 根木棍纵列，产出 1 把石锄。
- recipe ID `10`：2 个铁锭纵列旁接 2 根木棍纵列，产出 1 把铁锄。
- recipe ID `11`：横排 3 个小麦，产出 1 个面包。
- recipe ID `12`：纵向 2 个橡木木板，产出 4 根木棍。
- recipe ID `13`：2×2 橡木木板，产出 1 个工作台。

单格配方的形状可出现在归一化后网格的任一位置。recipe ID 只用于注册表与 UI 身份，新路径的线上消息 MUST NOT 携带 recipe ID，recipe ID MUST NOT 落盘。recipe `14..18`（火把、木剑、石剑、铁剑、白床）由本批次其余功能行在合流后追加，追加前查询这些 ID MUST 稳定拒绝。相同初始状态与命令序列经 Memory 和 TCP MUST 得到相同结果。

#### Scenario: 石砖配方可查询

- **WHEN** 系统读取 recipe ID `1`
- **THEN** 该配方稳定表示 2×2 石头转换为 4 个石砖

#### Scenario: 熔炉配方可查询

- **WHEN** 系统读取 recipe ID `2`
- **THEN** 该配方稳定表示 3×3 圆石圆环（中格为空）转换为 1 个熔炉

#### Scenario: 镐配方使用木棍

- **WHEN** 系统读取 recipe ID `4` 或 `5`
- **THEN** 该配方的形状为顶排三原料加中列两根木棍

#### Scenario: 木棍与工作台配方可查询

- **WHEN** 系统读取 recipe ID `12` 或 `13`
- **THEN** recipe `12` 稳定表示纵向两木板转换为 4 根木棍，recipe `13` 稳定表示 2×2 木板转换为 1 个工作台

#### Scenario: 单格配方的位置无关

- **GIVEN** recipe ID `7` 的单个橡木原木
- **WHEN** 原木分别放在 2×2 网格的四个格位
- **THEN** 四种摆放都匹配 recipe `7`

#### Scenario: 未登记配方被拒绝

- **GIVEN** 玩家具有任意有效完整物品状态
- **WHEN** 系统查询 recipe ID `0`、大于 `13` 的值或尚未由批次其余功能行追加的 `14..18`
- **THEN** 查询 MUST 稳定拒绝且不产生任何产物

#### Scenario: 既有配方编号不因新增而位移

- **GIVEN** 追加 recipe `12`、`13` 后的配方表
- **WHEN** 系统查询 recipe ID `1`..`11`
- **THEN** 每条的编号 MUST 保持不变，语义按本变更的形状表表达

#### Scenario: 锄头配方产出满耐久工具

- **GIVEN** 玩家网格摆放出 recipe ID `9` 或 `10` 的形状
- **WHEN** 玩家执行一次产物取出
- **THEN** 产出的锄头 MUST 具有该工具类型的满耐久，且匹配形状的每个非空格恰减 1

#### Scenario: Memory 与 TCP 的形状合成一致

- **GIVEN** 相同初始完整物品状态与相同的网格命令序列
- **WHEN** 场景分别通过 Memory 与 TCP 执行
- **THEN** 最终完整物品状态与拒绝结果 MUST 一致

### Requirement: 合成原子更新完整物品状态

服务端 SHALL 在网格与背包的副本上执行每次合成动作：产物取出按匹配形状对每个非空格恰减 1，再按既有稳定插入顺序把恰好一个完整产物放入背包；只有消费与产物放置都成功时才能原子提交。任何失败 MUST 同时保留全部原料与网格内容，MUST NOT 产生部分产物。旧聚合单输入路径的按栏位升序聚合扣料语义随本变更移除。

#### Scenario: 取出原子扣料并入包

- **GIVEN** 网格摆放出 recipe ID `1` 且背包可容纳 4 个石砖
- **WHEN** 玩家执行一次产物取出
- **THEN** 匹配形状的 4 个石头各减 1、背包新增 4 个石砖，产物格按剩余网格重新派生

#### Scenario: 原料不完整不部分扣除

- **GIVEN** 网格内只有 3 个石头且其余格为空
- **WHEN** 玩家执行产物取出
- **THEN** 产物格 MUST 为空，取出 MUST 稳定拒绝且网格与背包保持一字不变

#### Scenario: 产物无空间不消耗原料

- **GIVEN** 网格匹配某配方但背包无法容纳完整产物或消费后剩余网格
- **WHEN** 玩家执行产物取出
- **THEN** 服务端 MUST 稳定拒绝，网格与全部 36 格 MUST 保持不变

### Requirement: 合成遵循命令顺序并私有确认

服务端 MUST 按所属玩家的命令序列执行网格移动与产物取出；成功动作 SHALL 只向该玩家发布新的完整权威网格状态与（如有变化的）完整物品状态。客户端 MUST 只发送带序列的网格移动或取出命令，并在收到确认前保持最后确认镜像，MUST NOT 预测扣料、产物或网格移动。值域校验 MUST 拒绝越界统一视图格、两端同格、两端都在背包区以及个人网格扩展格的移动命令，MUST 拒绝携带零序列的取出命令。既有 recipe-click 命令保留线上注册但服务端 MUST 对其稳定拒绝且不改变任何状态（过渡语义，类型删除归批次集成）。相同初始状态和命令序列经 Memory 与 TCP MUST 得到相同结果。

#### Scenario: 过期序列不重复效果

- **GIVEN** 玩家已经成功处理 sequence `8` 的网格命令
- **WHEN** 同一玩家再次提交 sequence `8` 或更小的命令
- **THEN** 服务端不得再次移动物品、消费原料或发布新的网格与物品状态

#### Scenario: 成功取出只确认所属玩家

- **GIVEN** 玩家甲和玩家乙同时在线且甲的网格匹配某配方
- **WHEN** 玩家甲提交下一有效序列的取出命令
- **THEN** 只有甲收到新的网格状态与物品状态，玩家乙不收到甲的任何状态

#### Scenario: 客户端不预测合成

- **GIVEN** 客户端已显示最后确认的网格与物品镜像
- **WHEN** 客户端发送有效的取出命令但尚未收到服务端确认
- **THEN** 网格、背包和快捷栏 MUST 保持最后确认的原料与产物数量

#### Scenario: recipe-click 命令稳定拒绝

- **GIVEN** 任意在线玩家状态
- **WHEN** 客户端提交既有 recipe-click 合成命令
- **THEN** 服务端 MUST 稳定拒绝且完整物品状态与网格保持不变

#### Scenario: Memory 与 TCP 合成语义一致

- **GIVEN** 相同初始玩家状态和网格命令序列
- **WHEN** 场景分别通过 Memory 与 TCP 执行
- **THEN** 最终网格、完整物品状态、拒绝结果和持久化玩家状态 MUST 一致
