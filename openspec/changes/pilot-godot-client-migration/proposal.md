## Why

Mornlea's current graphical client concentrates Darwin windows, input, the WebView UI, and all GPU rendering in the in-house Rust `mornlea_client`, while the Go application layer still owns client mirrors, prediction, mesh scheduling, and per-frame presentation orchestration. Continuing on the current path preserves voxel-rendering control, but requires the project to build cross-platform windows, editor, audio, asset-import, and graphics-debugging capabilities itself; before deciding on a full migration, a minimal Godot client loop that does not touch the authoritative server is needed to validate integration cost, performance, and behavioral equivalence.

## What Changes

- Add a Godot pilot client that coexists with the existing Darwin client and connects to the authoritative server only through the existing TCP login and Play protocol.
- Establish `apps/mornlea-godot/` as a stable project root that Godot Project Manager can import directly; the pilot and the future production client reuse the same `project.godot`, Bootstrap, and host kernel rather than moving directories again during a later full migration.
- Fix the Godot client's platform scope to desktop: current Darwin/macOS is the first implementation and pilot environment, and only future Windows and Linux desktop releases are reserved; do not design Android, iOS, Web, or console directories, input, lifecycle, or export paths.
- Make Python the primary language for the Godot host, feature orchestration, desktop adaptation, and presentation scripts through one exactly pinned, project-hardened derivative of the community Py4Godot GDExtension. The derivative is reproduced from an exact upstream source revision plus a repository-owned minimal patch stack; it is not a second gameplay/data bridge and may change only interpreter isolation, editor integration, packaging, and lifecycle correctness. Retain only a pure-GDScript bootstrap/diagnostic loader so the project remains directly openable when native artifacts or the Python runtime are missing; new gameplay features MUST NOT be implemented in GDScript by default.
- Keep protocol reception, client mirrors, input prediction, and presentation snapshots in Go; Godot owns only windows, input collection, GPU presentation, the pilot UI, and resource lifecycles, and does not own gameplay resolution or authoritative world state.
- Define a versioned, capacity-bounded client-core boundary for the Godot adapter that does not publish partial results on failure, covering connection, input, world deltas, camera, entities, weather, minimum HUD state, and disconnection.
- Organize Godot presentation capabilities with an explicit feature catalog, coarse-grained feature manifests, and evolvable ABI feature families; `session`, `player_view`, `world`, `actors`, `ui`, and `platform` each form a vertical functional boundary, while ordinary scenes/components are not registered as independent plugins. Later production terrain, full entities, UI, audio, local mode, tooling, and release capabilities expand through added or replaced features rather than being hard-coded in the pilot main scene or a single giant snapshot.
- Reuse the production mesh, lighting, collision, raycast, and physics implementations from `mornlea_engine`; the pilot MUST NOT add a second numerical or prediction implementation in Python, GDScript, C#, or another Godot-side language.
- Treat the Python binding as a replaceable scripting-runtime adapter rather than a new gameplay authority or data bridge. Python may call the project-owned `MornleaClientBridge` only through Godot-visible typed methods and signals, and MUST NOT call the Go or engine C ABI directly, import the standalone companion Agent service, perform runtime package installation, or own unbounded per-frame work.
- Preserve the rejected upstream Py4Godot `4.7-alpha21` qualification as evidence, and maintain the approved hardening as reviewable patches under `scripts/godot/py4godot/` rather than vendoring an untraceable source tree. Pin upstream source, patch-series digest, build inputs, output artifact digest, embedded CPython, licenses, and current macOS target. Every patch must state its runtime defect and deletion condition, and the complete qualification matrix remains mandatory.
- Use existing fixed scenes, visual baselines, and benchmarks to establish comparable reports for the legacy Rust client and the Godot pilot; the Godot pilot generates only untracked evidence under `build/visual/godot-pilot/`, and does not add renderer-specific golden categories or overwrite currently tracked baselines. Performance figures are recorded only, while capacity overflow, data loss, incorrect identity, and I/O failure remain hard failures.
- Produce a phased migration table covering the principal client capabilities on current `main`, their dependencies, entry/exit criteria, and rollback strategy; this change's implementation scope ends with the remote TCP vertical slice and a migration-feasibility conclusion.
- Retain the existing production paths for `mornlea`, capture, benchmark, Memory single-player assembly, the React/WKWebView UI, and client ABI v19; if the pilot fails, the new entry point can be removed without migrating saves, protocol, or server.

User-observable outcome: developers can open the stable Mornlea Godot project directly from Godot Project Manager; even when native libraries or the pinned Python runtime are not ready, the editor opens and displays actionable preparation diagnostics. After explicit bootstrap completes, Python-authored features can start an independent Godot pilot client, connect to the existing dedicated server, enter the world, and perform movement, look control, terrain deltas, target feedback, at least one remote entity type, a basic HUD, and disconnection handling; the player's default startup path and existing visual behavior remain unchanged.

Non-goals: this change does not delete `mornlea_client`; move the server, world state, saves, companion Agent, or authoritative tick into Godot; reuse or embed `packages/agent` as the client scripting runtime; port numerical or protocol logic to Python; implement local Memory mode, complete menu/container UI, all visual effects, or production cross-platform release; or change the live protocol, save schema, engine ABI, or client ABI. Reserving stable extension contracts for those later capabilities does not implement them early within this change. Mobile, Web, and console support are outside the reserved scope of both the current and future P8–P14 route; if needed in the future, they require a separate new initiative.

## Capabilities

### New Capabilities

- `godot-client-pilot`: Defines the Godot pilot client's authoritative boundary, minimal remote gameplay loop, error/capacity behavior, comparable validation, and rollback conditions.

### Modified Capabilities

None. The existing Rust graphical client and its window, rendering, UI, capture, and benchmark behavior remain unchanged.

## Impact

- Expect to add `apps/mornlea-godot/` as the stable Godot project root, layered internally as a pure-GDScript `app/bootstrap/`, Python `app/host/`, Python-led `features/` coarse-grained vertical capabilities, Python `platform/desktop/` device adaptation, generated `addons/py4godot/` hardened scripting runtime, `addons/mornlea_bridge/` project-owned native data boundary, `shared/` common presentation resources, and `assets/generated/` deterministic import artifacts; also add a platform-independent Go client-core/bridge package and a minimal reproducible Py4Godot patch/build stack under `scripts/godot/py4godot/`.
- `platform/` permits desktop adaptation only, and release targets permit only `macos`, `windows`, and `linux`; the pilot requires only the current macOS development machine, with Windows/Linux deferred to a later desktop-release change.
- Reuse the platformable mirror and prediction capabilities in `packages/shared/network`, `packages/shared/core`, `packages/shared/physics`, `packages/shared/nativeabi`, and `packages/client/client`.
- Identify and extract frame-advance and presentation-snapshot responsibilities that do not depend on Darwin/window/renderer from `packages/client/cmd/mornlea/app`, without allowing the Godot adapter to import server packages.
- `packages/engine/crates/mornlea_engine` and engine ABI v11 remain unchanged; `packages/engine/crates/mornlea_client` and client ABI v19 retain their existing production identity.
- Add Godot project-root closure, Python/GDScript ownership, locked Python-runtime, no-runtime-install, feature-contract, export-exclusion, dependency, authoritative-boundary, platform-resource, visual-producer ownership, and no-second-implementation guards in `packages/audit`; add optional Godot bootstrap, Python checks, asset-sync, build, and validation entry points in `scripts/godot/`, the Makefile, and CI.
- Protocol compatibility: continue using protocol v44 and add no packets or compatibility layer; version mismatches continue to be rejected by the existing handshake.
- Save compatibility: do not read or write world/player saves; the pilot connects only to a server, so schemas do not change.
- Concurrency impact: only bounded, immutable, revisioned batches pass between Go reception/prediction and the Godot main thread; Python/GIL execution on the rendering main thread MUST NOT wait on network, disk, runtime package installation, or unbounded numerical or mesh work.
- Performance impact: zero impact on the existing production client; the pilot separately records Python host/apply time and allocation pressure in addition to CPU/GPU frames, chunk upload, loading, memory, and input latency, with reports bound to the existing benchmark identity.
