# B-34 生存初始背包留空（design）

## 上下文与数据所有权

本 change 只改动三处既有的所有权边界内，不新增包、不新增跨包依赖：

- `packages/shared/core`：配方表（`recipe.go`）、掉落表（`item.go` 的 `BlockDrop`）、熔炼表（`smelting.go`）——物品可获得性的单一真源。新增的价值闭包守卫测试放在此模块的既有测试面内。
- `packages/server/sim/entity`：采掘规则 `miningRule` 是「何时能取得掉落」的单一真源（含工具门槛与 `harvestable` 语义）。空背包起家的**规则级**闭包守卫落在这里，因为它必须求值真实采掘规则；该包不得导入 `packages/shared/worldgen`（`packages/audit/dependency_test.go:79`），因此自然来源方块集合以带溯源注释的显式常量表达。
- `packages/server/server` 与 `packages/server/server/persistence`：缺失玩家快照的构造，以及端到端脚本与登录就绪判定。

并发边界不变：变更不触碰权威 tick 热路径，不新增 goroutine、通道或共享状态；空背包只是缺失玩家快照构造时的一个取值变化。跨 goroutine 发送成功后的消息仍视为不可变。

## D1：缺失玩家的初始背包恒为空

`newMissingCachedPlayer` 不再设置 `Inventory` 字段（`core.Inventory` 零值即九格快捷栏 + 27 格背包全部空槽）。删除 `starterMaterialItems` 与 `starterMaterialInventory()`，不保留「空清单」形式的残留符号：保留一个永远返回空的构造函数会让读者以为还存在可配置的发放机制。

**被否决的替代方案**：把清单改短（例如只留原木与木板）——那仍然是「一次性发放」，与本行「在关键资源已有自然取得路径后移除」的目标冲突，且会重新引入「哪些材料该发」的持续裁决成本。

## D2：登录就绪判定不得以「背包非空」为信号

`farming_loop_e2e_test.go` 与 `hunger_loop_e2e_test.go` 用 `message.Inventory != core.Inventory{}` 作为「已收到携带权威背包的玩家状态消息」的代理信号。空背包使该条件永不成立，脚本会空转到等待预算耗尽（`integrationLoginTickBudget`）并以超时形式报红——这是一种读不出原因的红。

修复方式：把就绪信号改为「收到了携带权威背包的玩家状态消息」这一事实本身，而不是背包内容。契约是**空背包也必须能判定为就绪**；实现由任务选择（例如以消息到达计数或该消息的到达为信号）。不得放宽等待预算。

## D3：圆石缺口的裁决（本 change 的关键裁决）

侦察结论：`ItemCobblestone` 在新世界**只有材料包一个来源**。`CobblestoneID` 不参与世界生成（`packages/shared/worldgen/generator.go:137-144` 的 15 项材料表无圆石；无岩浆；无结构生成），其物品生产者只有 `BlockDrop(CobblestoneID)`。消费圆石的是 `RecipeFurnace`（3×3 圆石圆环）与 `RecipeStoneSword`（纵向 2 圆石）。

若只清空材料包，则熔炉、整套熔炼（铁锭、玻璃、砖块、熟牛肉）、铁制工具与**已交付的空桶（B-02，需 3 铁锭）**一并永久不可达——本行会回退既有已交付内容。因此裁决：**把这两条配方改用可徒手取得的石料（`ItemStone`）**。

理由：(a) `ItemStone` 已是本仓石料的规范材料——石砖、石镐、石锄全部以它作原料，而圆石只是不参与生成的装饰方块；让熔炉与石剑继续以装饰材料为原料本身就是材料经济里的一个不一致。(b) 本裁决是纯 Go 侧的配方表改动，不涉及世界生成、engine ABI、golden 与版本矩阵。(c) 世界生成层补圆石（见否决项）会改写新生成区块并牵动 golden，且与后续「基础洞穴生成」行的边界重叠。

**被否决的替代方案**：

1. 世界生成圆石矿脉或地表圆石：改动 Rust worldgen 与材料表编码，新生成区块逐字节改变，牵动 worldgen golden 与既有区块改写论证；收益只是把装饰材料变成可获得，而本行的验收面（四条关键能力）并不需要它。
2. 新增「石料 → 圆石」的合成或熔炼配方：熔炼需要熔炉，而熔炉本身正需要圆石，构成循环；合成则等于凭空增加一条无语义依据的配方。
3. 把 `StoneID` 的掉落改为圆石：会反噬石砖、石镐、石锄三条既有配方与全部采掘测试，爆炸半径远大于收益。
4. 保留材料包但缩小到「关键材料」：见 D1 的否决理由。

本裁决的后果被显式接受：圆石、平滑石、苔藓圆石、白色羊毛、红色瓦块这五种不自然生成的装饰材料在空背包新世界里不可获得。它们不是任何关键能力路径的必需输入（由 D4 的守卫钉住），其自然化登记为后续行 `装饰材料自然获取路径`（见 tasks Task 7）。

## D4：价值闭包守卫是「可达性」的可判定形式

「锁定新世界可达性」实现为一个**规则级价值闭包守卫**，落在 `packages/server/sim/entity`（可调用真实 `miningRule`）：

- 起点：自然来源方块集合（带溯源注释的显式常量，逐项注明来自 worldgen 材料表、矿石规则、树木规则或短草规则），加上自然生成的作物与被动生物掉落。
- 规则：`miningRule`（含工具门槛：空手不可采收的方块需要先在闭包内取得对应工具）、`core.BlockDrop`、`core.Recipe`、`core.SmeltingOutput`、工具耐久损坏映射。
- 求不动点后断言两侧：
  - **正向**：工作台、火把、至少一种镐、面包或熟肉在闭包内；熔炉、铁锭、空桶也在闭包内（保证不回退 B-02/B-27/A-03 的已交付内容）。
  - **反向**：物品注册表中不在闭包内的物品集合**恰好**等于显式声明的「已接受不可获得集合」。任何新配方以不可获得物品为必需输入、或任何物品悄悄失去来源，都会让这条断言变红——这正是本行侦察中发现圆石缺口的那一类缺陷。

反向断言要求把 `ItemPotato`/`ItemCarrot`/`ItemPoisonousPotato` 一并列入已接受集合：它们的唯一来源是「种下该物品后长成的作物」，而物品本身没有自然来源，属于 B-01 遗留的既有缺口（先于本 change，不由本行引入）。守卫把这个既有缺口显式记名，并由 Task 7 登记为后续行，而不是让它继续隐形。

守卫与 D3 互为闭环：先由裁决消除熔炉/石剑对圆石的依赖，再由守卫证明「除已接受装饰材料外，注册表内每个物品都有自然来源」。

**被否决的替代方案**：只写一个端到端脚本（D5）作为可达性证明——端到端只能覆盖被走通的那一条路径，无法对未来新增的「配方以不可获得物品为原料」类缺陷报警；反之只写闭包守卫也不够，它证明的是规则表自洽，不证明规则真的接进了世界。因此两者都要，且分工写进 tasks。

## D5：空背包起家端到端冒烟

在 `packages/server/server` 新增一个真实生成世界 + Memory transport 的脚本化冒烟：从空初始背包出发，只用手动采掘与合成推进「原木 → 木板 → 工作台 → 放置 → 3×3 网格 → 石镐」，用来证明守卫里的规则真的接进了世界（规则表与世界接线之间的缝隙是守卫看不见的）。脚本不得使用 `SetPlayerInventoryForTest` 之类直给物品的测试后门来替代任何一步；为在有限预算内确定性地找到树与石头，允许把脚本置于缺省世界生成的确定性坐标上，但**不得**用夹具改写方块。

## D6：守卫与措辞的连带更新

- 跨模块源码守卫 `packages/shared/core/sapling_acquisition_test.go` 的第三条腿按源码文本解析材料包清单；清单删除后该守卫会以「未找到声明，本守卫会静默失效」报红。改指新契约：断言缺失玩家初始背包的构造处不出现树苗标识符，且守卫在找不到目标时仍然失败（不允许静默失效）。
- `oak-sapling-regrowth` 主规格中「树苗 MUST NOT 通过合成、初始材料包或任何其他途径获得」的措辞随概念消失改为「新玩家初始背包」，语义不变。

## 风险与回退

- 风险一：配方原料变更影响既有测试夹具（用圆石摆出熔炉/石剑形状的测试）与客户端配方书。缓解：Task 3 要求同时更新受影响测试与客户端侧的原料呈现，并以 `make dev-check` 覆盖六模块。
- 风险二：`git blame` 意义上的「历史材料包」仍存在于老存档；本 change 明确不迁移、不回收，由 persistence 测试的「已有玩家逐槽保留」场景钉住。
- 风险三：端到端冒烟对世界生成的确定性依赖（树与石头的位置）。缓解：脚本按缺省种子在确定性坐标上推进，且不依赖概率掉落（种子不是本冒烟的必经步骤）。
- 回退：revert 分支即可，无数据迁移与版本号回滚；唯一残留影响是新玩家不再获得材料包，回退后自动恢复。

## 验证方法

- 转移验证：`go test ./packages/shared/core ./packages/server/sim/entity ./packages/server/server/... -race -count=1`。
- 既有脚本不回归：`tests` 层的 farming/hunger 端到端脚本（含 TCP parity 共用 runner）必须全绿，且不得靠放宽等待预算通过。
- 阶段边界：`make dev-check`、`make test-race-changed`，收尾按 tasks Task 7 的六模块全量 race 与 `openspec validate --all --strict --no-interactive`。
- 版本矩阵核验：本 change 不改变协议、schema、ABI 与 scenario，Task 7 必须给出「矩阵未变」的实际核验证据（`packages/audit` 版本基线测试 + 逐项确认）。
