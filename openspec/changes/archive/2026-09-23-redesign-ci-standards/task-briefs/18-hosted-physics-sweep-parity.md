## Fixed contract and algorithm

`stepSweepBounds` must use the same vector length as Rust `vec3_len` for the movement target, the delta in `moveToward`, and airborne speed clamp. Rust computes `v[2].mul_add(v[2], v[0].mul_add(v[0], v[1] * v[1]))`, converts the resulting `f32` to `f64` for square root, then converts back to `f32`. Go `mgl32.Vec3.Len` uses an unfused expression on Linux/amd64, whereas Go/arm64 may fuse it. Introduce an unexported step-local length helper whose explicit `math.FMA` calls and `float32` conversion reproduce the two Rust fusion boundaries and operand order; use `float32(math.Sqrt(float64(sum)))` for the final root. Normalize with `l := 1 / length` followed by component multiplication, matching Rust and `mgl32` order. Do not use `math.Hypot`, rearrange the terms, or widen the native tolerance.

Keep `movementTargetFromYaw` as the single target helper rather than copy a second integrator; its existing sneak-edge consumer must continue using the corrected direction. Keep the source comment in English and explain why the explicit fused sequence is needed. `moveToward` is used only by the fixed-step envelope; calculate its delta length once and reuse it for comparison and scaling. Other vector operations retain their current order. If arithmetic evidence shows another order mismatch, stop and report exact input/bits before widening the edit.
