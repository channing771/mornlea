## Execution And Review Protocol

以下 1.1–8.1 均是一个可由单个 fresh implementer 在一次会话内闭合的实现任务。每项都必须按以下 SHA 流程执行，控制会话不得直接实现：

1. 从 ledger 记录的精确 task baseline 开始，先补可观察失败测试并记录 RED；
2. 完成最小实现、重构并提交不含 `tasks.md`/`ledger.md` 的 code/test commit `C`；
3. 在实现与工作树干净的候选 SHA 上执行 focused verification；该 SHA 是 candidate `I`；
4. 由独立于 implementer 且彼此独立的 fresh SPEC reviewer 与 QUALITY reviewer 裁决 candidate `I`；R1–R3 由原 implementer 修复，R4–R5 换 fresh implementer，每轮 repair 都重新提交、重新执行 focused verification 并形成新的 candidate `I`，超过五轮由控制会话逐条写 `Ruling:`；
5. 只有最终 clean verified implementation SHA `I` 的 focused verification 与双评审都 PASS 后，控制会话才提交只含本任务 checkbox 与 ledger 证据的 tasks/ledger-only evidence commit `L`。`L` 不得冒充 `I`，下一任务 baseline 必须包含上一任务 `L`。

所有实现任务开始前都要重新阅读本 change 的 `proposal.md`、十一份 delta specs、`design.md`、本文件及目标目录祖先链 `AGENTS.md`。涉及 Rust 的任务在 clean baseline 先运行 `make rust`；发现设计或规格不成立时先停下并修订 OpenSpec 产物，不得让代码先行。每项必须在 ledger 记录 baseline、implementer、RED、`C`、最终 `I`、绑定 `I` 的 focused verification、SPEC/QUALITY、repairs、`L` 与最终 `Ruling` 后才能勾选。实现提交与 repair 提交信息必须是单行英文 `<type>(<scope>): <subject>`。

- [x] 9.2 在 whole-change 双评审 PASS 且工作树只含预期改动后，先冻结并记录一个 clean verified implementation SHA，再在该精确 SHA 执行完整 T3，逐条把命令、耗时与输出摘要写入 ledger：`make rust`；`make rust-check`；`test -z "$(gofmt -l .)"`；`go vet ./...`；`go test ./... -race -count=1`；`go test ./internal/archcheck -count=1`；`make test-multiplayer`；`make visual-check`；复核同一 SHA 的 v21 record-only 报告与 `perfcheck` self-compare；`openspec validate natural-grass-seeds --strict --no-interactive`；`openspec validate --all --strict --no-interactive`；`git diff --check`。性能数值不得改变退出状态，报告结构/身份、真实 overflow、数据丢失、I/O、ABI 和视觉 compare 失败仍必须硬失败；自动门禁不得启动或聚焦前台游戏窗口。T3 全绿和最终裁决完成后，控制会话才创建只含 `tasks.md`/`ledger.md` checkbox 与证据的 evidence commit；该提交不得回写或声称包含自己的 SHA，也不得冒充 T3 verified implementation SHA。evidence commit 后的 closure validation 只复核 documentation-only scope、named/all strict OpenSpec、`go test ./internal/archcheck -count=1` 与 `git diff --check`，不因纯证据提交重跑 full T3。

完成全部 checklist 后，控制会话记录 closure evidence state 与 sync baseline，按 `openspec-sync-specs` 审阅并沉淀十一份 delta 到主规格，记录同步提交、reviewer、裁决并运行 named/all strict、archcheck 与 diff-check；随后记录 archive baseline，按 `openspec-archive-change` 归档并记录归档提交、归档前后 `openspec validate --all --strict --no-interactive` 与 active/archive 唯一性。backlog/current progress、PR/CI 与合并属于控制会话收尾，不由任一 implementer 提前执行。
