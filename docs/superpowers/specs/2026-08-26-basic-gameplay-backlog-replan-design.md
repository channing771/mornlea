# 基础玩法任务池重排设计

日期：2026-08-26

## 1. 背景

当前规划表把三类性质不同的工作都标成「未认领」：依赖已经满足、可以立即实现的功能；已有明确需求但被前序阻塞的功能；以及红石、多维度、Rust 状态下沉等尚未拆成可评审闭环的方向性工作。实现者只能从备注中人工推断依赖和文件冲突，因此表面上有大量候选，实际领取后经常发现版本号、ABI、编号或文件所有权已经被其它行占用。

第一夜生存批次进一步放大了这个问题。A-01..A-05 被设计为五路并行，A-06 统一合流，A-07 统一升版和生成 golden，A-08 再统一终审归档。任何一条功能线没有完成，已完成分支也不能独立合入；共同基线之后新增的 client ABI、engine ABI、capture 场景和文档分层又持续令批次里的预分配版本失效。

本次重排以「首夜生存 + 自给家园」为近期产品边界。Mornlea 仍是独立体素游戏，不追求兼容 Minecraft 的协议、存档或版权资源；这里的“基础玩法”只表示采集、制作、照明、战斗、过夜、种植和可再生资源能够构成连续可玩的生存闭环。

## 2. 已核实现状

当前代码已经具备权威采掘、石/铁工具与耐久、世界材料和矿石、熔炉、箱子、方块放置、生命、饥饿、进食、农业、昼夜、水体、游泳、氧气、死亡重生及玩家近战。最影响基础玩法闭环的缺口是：

- 图形客户端仍只有固定 recipe-click 合成；A-01 的格子工作台实现尚未合入。
- 世界没有敌对或被动生物，昼夜与住所对生存没有实质压力。
- 火把、剑、床和个人重生点仍在第一夜批次中。
- 新玩家由一次性材料包获得十四组整栈材料和 64 颗种子，采集与制作进度被大幅跳过。
- 种子和木材没有完整的自然再生入口，水不能搬运，食物只有小麦面包。

A-01 分支已按原规格实现并通过分支评审，但原规格明确排除拆分堆。其 ledger 已记录真实可玩性问题：镐、锄、熔炉、箱子等形状配方要求把同一种材料放进多个格，而整堆移动只能把整组材料放入一个格；当前唯一绕路是主动丢弃单件、等待 40 tick 拾取延迟，再把主栈和拾回物分别放入网格。该行为不能作为基础工作台的正式交互，因此 A-01 在合入前必须补最小的权威拆分语义。

当前工作树事实如下：

| 行 | 当前事实 | 重排处置 |
|---|---|---|
| A-01 | 分支干净，实现与双评审完成 | 重开最小拆分语义，再由本行自行集成 |
| A-02 | proposal 已提交，`core/assets/physics` 有未提交实现 | 原样保护，A-01 合入前不 rebase、不清理 |
| A-04 | proposal/design 已批准，无功能实现 | 保留设计证据，转为排队且不占文件 |
| A-05 | 只有 docs-only claim | 释放预占，转为排队 |
| C-08 | 规划表显示已认领，但没有对应 worktree、分支或开放 PR | 转为设计候选；历史认领记录保留在备注和 Discussion 评论 |
| E-12 | worktree 有未提交实现 | 允许原认领者收尾，不因本次重排丢弃 |

## 3. 目标与非目标

### 3.1 目标

- 规划表直接区分「可领取」「已排队」「尚待设计」，实现者不再靠阅读几十行备注猜测可行性。
- 把第一夜批次改为逐项合入的串行发布列车，保留已经完成和正在进行的成果。
- 每个功能行自行完成最终编号、版本、golden、基线文档、OpenSpec 归档与 PR，不建立末端大爆炸集成任务。
- 冻结首夜和自给家园的近期执行顺序；完成前不自动领取伙伴扩展、大型架构迁移或远期世界系统。
- Discussion #71 继续是 `docs/feature-backlog.md` 的自动生成镜像，未知状态或遗漏行必须硬失败，不能静默消失。

### 3.2 非目标

- 本次不修改游戏代码、协议、存档、ABI、benchmark、capture 场景或 golden。
- 本次不实现 A-01 拆分语义或其它玩法；这里只改变规划与自动领取规则。
- 不删除现有功能分支、worktree、未提交改动、OpenSpec 产物或历史 Discussion 评论。
- 不为所有远期功能写完整设计；设计候选只有重新经过 brainstorming、拆成独立闭环后才能晋升。
- 不引入排期日期、工时估算、优先级打分器、自动依赖求解器或新的项目管理服务。

## 4. 方案比较

### 4.1 采用：串行救活现有工作

保留 A-01 的已完成实现、A-02 的在途改动和 A-04 的设计成果，按单一核心玩法列车逐项完成。前序合入后，planner 才把下一行晋升为 `就绪` 或恢复原认领者继续开发。

优点是不会丢弃已付出的实现与评审成本；版本和编号在真实合入基线上确定；每行都可独立回退。代价是首夜五项不能并行，但这正好消除当前最主要的合流和所有权阻塞。

### 4.2 否决：放弃 A 批次，重做最小首夜竖切

只实现「可吃面包 + 一种夜间敌怪 + 玩家可攻击」，可更快产生最小战斗闭环，但会丢弃 A-01 已完成成果和 A-02 进行中成果，也会把工作台、火把、剑和床再次留成半成品。总返工高于串行完成现有工作。

### 4.3 否决：保留五路并行，只补依赖标签

这是文档改动最少的方案，但共享编号、协议、ABI、golden 和基线文档仍由 A-06..A-08 统一收口。它只能更清楚地说明为什么任务不能领取，不能消除阻塞本身。

## 5. 状态模型

规划表采用以下状态：

| 状态 | 含义 | 是否可由实现者领取 |
|---|---|---|
| `就绪` | 需求已明确，依赖、版本槽和文件冲突均已清空 | 是，唯一可领取状态 |
| `已认领` | 正在执行 brainstorming 或 OpenSpec 设计，尚未改功能代码 | 否，只有原认领者可继续 |
| `开发中` | 已进入功能实现或验证 | 否，只有原认领者可继续 |
| `待集成` | 实现与任务评审完成，等待本行自己的归档、PR 或合入 | 否，只有原认领者可继续 |
| `排队` | 行已经足够明确，但前序未完成；不占版本号或文件 | 否 |
| `设计候选` | umbrella、推测性或远期能力，尚不能形成独立实现闭环 | 否 |
| `已完成` | 已合入 main 并完成归档 | 否 |
| `已取消` | 被其它流程取代或不再需要；保留历史原因 | 否 |

`未认领` 状态退出当前规范。它同时表达「可领」和「无人负责」，无法区分阻塞与就绪；改为 `就绪` 后，状态本身就是自动领取的完整门禁。

同一时间只允许一个会推进稳定编号、协议、存档 schema、engine/client ABI 或 capture golden 的核心玩法行处于 `就绪`、`已认领`、`开发中` 或 `待集成`。不影响版本且文件集合确实不交叠的小型修复可以并行；不得再用整个 package 的长期独占代替具体冲突分析。

## 6. 首夜发布列车

执行顺序固定如下，但版本号只在各行基于当时 main 确定，不在规划表预占绝对值。

### 6.1 A-01 权威格子工作台

A-01 保留现有 2x2/3x3 权威网格、形状配方、回收不变量、工作台方块和私有同步实现，并在合入前扩充最小拆分语义：玩家必须能从背包中的一个材料堆，把单件权威转移到多个合成格。详细鼠标动作、消息载荷和序列语义由 A-01 的 OpenSpec 更新裁决，但范围必须满足以下边界：

- 服务端仍是物品数量和移动结果的唯一权威。
- 失败必须保持来源、目标、网格和背包逐格不变。
- 必须覆盖同一材料分布到多个格后成功制作现有镐、锄、熔炉或箱子配方的端到端场景。
- 不实现鼠标 cursor stack、拖拽铺放、shift-click、配方书或通用容器自动整理。

A-01 自行删除过渡 recipe-click 线上语义、确定最终协议版本、处理受影响 capture/golden、同步基线、归档并合入。原 A-06/A-07 中属于工作台的职责回收到本行。

### 6.2 A-02 可放置火把

A-02 等 A-01 合入后再保存当前工作、整理并基于最新 main 继续；不得在工作树仍有未提交改动时执行 rebase。火把自行追加届时可用的方块、物品、配方和 model 契约，并使用届时 next engine ABI，不沿用已被占用的旧绝对版本。其 capture/golden、基线和归档由本行完成。

### 6.3 A-03 三级剑与统一战斗

A-03 在工作台和火把合入后实施。剑配方使用已经稳定的格子合成语义；玩家与敌怪的统一命中结算只抽取真实存在的共同规则，不提前建设通用 ECS 或多实现接口。该行自行处理所需协议确认和版本演进。

### 6.4 A-04 权威近战夜行者

A-04 保留已批准的确定性生成、上限、寻路、持久化和呈现设计，但从 A-02 消费服务端可查的发光属性，从 A-03 消费已落地的战斗结算。功能分支不再等待 A-06 接线；敌怪攻击、玩家反击、掉落、重启和多人发布必须在本行闭环。

### 6.5 A-05 床与睡眠

A-05 在夜行者合入后实现双格床、睡眠跳夜、敌怪阻睡、个人重生点和相关存档。床的模型分派、版本、golden、迁移和归档都由本行完成。

### 6.6 取消末端批次行

A-06、A-07、A-08 标记为 `已取消`，备注说明其合流、版本/golden 和终审职责已分别回收到 A-01..A-05。历史设计和计划保留，不改写为当前事实。

## 7. 自给家园发布列车

首夜列车全部合入后，按以下顺序逐行晋升：

| 顺序 | 行 | 最小可玩结果 |
|---|---|---|
| 1 | B-04 草丛与自然种子 | 世界提供可再生种子入口；同一行取消新玩家固定 64 种子赠送 |
| 2 | B-02 水桶 | 可原子舀取和放置水源，农田不再绑定天然水岸；无限水源规则在本行裁决 |
| 3 | B-33 树苗与橡树再生 | 只交付一种树苗和有界确定性生长，令木材可再生；不建设通用植被系统 |
| 4 | B-27 单一被动生物与熟食 | 只交付一种被动生物、原肉、熟肉和一条熔炉配方；复用已证明的实体路径，不先建 ECS |
| 5 | B-34 生存初始背包 | 在关键材料已有自然取得路径后移除十四组整栈大礼包，并以新世界可达性测试锁定不会软锁 |

B-01 只保留「更多作物」候选；肉类与熟食继续归 B-27。B-33、B-34 是本次新增规划行，来源为本设计。

## 8. 后续基础玩法与停车区

完成自给家园之前，以下基础玩法保持 `排队`，不进入自动领取池：门、冲刺、难度、护甲、远程战斗、完整分堆与快捷搬运、斧/铲、洞穴。现有 B-17、B-30、B-11、B-24、B-23 可直接承载前五项；后三项由 planner 按本设计新增连续 B 组行，但只能在前序闭环完成后逐项晋升。

下列方向统一标为 `设计候选`：伙伴后续扩展；Rust 阶段 3..5；世界 goroutine 分片；红石；多维度；完整生物群系；数据驱动方块模型；第二类敌怪抽象/ECS；完整状态效果；复杂流体和呈现扩展；非基础 UI 与材质扩展。它们没有被否决，只是不再伪装成可立即实现的任务。

在途 E-12 允许原认领者完成。C-08 因不存在对应 worktree、分支或开放 PR，释放为设计候选；若外部执行者能提供未同步证据，先恢复证据再裁决状态，不覆盖其工作。

## 9. 自动化与文档改动

### 9.1 单一真相源

`docs/feature-backlog.md` 继续是唯一规划来源。文件顶部新增近期产品目标和串行队列表；各能力表保留完整历史、来源和备注。依赖继续用行 ID 写入备注，不引入自动依赖求解器。

### 9.2 Planner 与 Implementer

- planner 新增的已确认功能默认进入 `排队` 或 `设计候选`，不得默认进入可领取池。
- planner 只有在前序已完成、没有版本槽冲突且工作树证据一致时，才能把队首一行晋升为 `就绪`。
- implementer 与接力循环只选择 `就绪`；没有 `就绪` 行时正常终止，即使表中仍有大量排队或设计候选。
- 已认领行异常中断仍按原恢复规则续跑，不重新领取。

### 9.3 Discussion 镜像

`scripts/agents/refresh-discussion.py` 按新状态生成 Discussion #71，正文至少展示完成、开发中、已认领、待集成、就绪、排队、设计候选和已取消分组。只有 `就绪` 使用绿色可领取标记。

生成器必须验证每个解析到的规划行恰好进入一个状态分组；未知状态、空状态或遗漏映射返回非零，不得静默从 Discussion 消失。远程更新仍只在完整正文构造成功后执行。

`scripts/agents/relay.sh` 的终结条件从「没有未认领」改为「没有就绪」。相关 `docs/development-process.md`、`docs/agents/README.md`、planner/implementer 角色卡与实际 prompt 必须使用同一状态词和领取语义。

## 10. 验证

本次规划重排不运行游戏构建或视觉更新。实现计划至少包含以下检查：

- 对 Discussion 生成器运行正常表、未知状态、空状态和全部非就绪状态用例，确认正常输出与 fail-closed。
- 运行生成器 dry-run，确认规划表每一行恰好出现一次且只有 `就绪` 位于可领取组。
- 验证 relay 在存在 `排队`/`设计候选` 但没有 `就绪` 时终止，在存在 `就绪` 时继续。
- 运行受状态解析影响的 agent dashboard Go 测试。
- 搜索全仓受控文档与脚本，确认不再把 `未认领` 当作当前领取状态；历史归档与 Discussion 旧评论不批量改写。
- 运行 `git diff --check`、相关脚本语法检查和 `go test ./cmd/mornlea-agent-board -count=1`。
- 先以 dry-run 检查 Discussion 正文，再使用 `--update` 刷新 Discussion #71；远程更新失败时仓库文件保持真相源，不回滚本地规划提交。

## 11. 风险与回退

- **A-01 范围重开**：拆分语义会增加协议与 UI 工作。它是形状合成真实可用的必要条件，且范围被限制为背包到合成格的最小权威转移，不扩展为完整鼠标手持栈系统。
- **A-02 未提交工作**：任何自动 rebase 或清理都会造成数据丢失。规划和执行 brief 必须明确先保存当前工作，再在 A-01 合入后人工协调。
- **吞吐下降**：核心玩法改为串行后并行数量减少，但每条线都能独立合入，消除了当前已经发生的版本漂移和末端等待；实际交付吞吐预计提高。
- **状态迁移遗漏**：Discussion 生成器的恰好一次分组校验防止新状态被静默忽略；仓库表仍是回退和恢复依据。
- **远期任务被遗忘**：设计候选仍保留 ID、来源与备注，只退出自动领取池，不删除历史。

若新状态模型影响自动化超出预期，可整支 revert 本次规划提交；它不改变产品协议、存档、ABI 或任何玩家数据。
